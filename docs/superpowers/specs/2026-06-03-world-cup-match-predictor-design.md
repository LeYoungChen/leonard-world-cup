# 世界杯胜负概率预测 Skill 设计文档

## 目标

创建一个可跨 agent 使用的 skill / workflow，名称暂定为 `world-cup-match-predictor`，用于预测 FIFA 世界杯比赛的胜 / 平 / 负概率。

对外包装要简单：用户输入一场世界杯比赛，skill 输出双方胜率、平局概率、置信度和几条清晰理由。

内部逻辑要专业：每次预测都实时检索公开网络信息，检查来源质量，把球队基本面、赔率隐含概率、市场信息流、伤停和赛程背景合成一个可解释的概率判断。

这个 skill 不是任何个人研究者的资料包，也不是把某位教授或某个团队的个人信息放进 skill 里。相关研究只作为方法论来源：足球比分统计建模、固定赔率市场效率、市场微结构、Agent-Based Modelling、Reinforcement Learning、风险控制和概率校准。skill 真正运行时，必须基于当前比赛的公开信息和建模流程，而不是基于静态人物资料。

虽然当前实现会优先落在 Codex skill 目录里，但文档、资源和输出格式都要尽量保持平台无关。其他 agent 即使没有 Codex 的 skill 机制，也应该能通过读取 `SKILL.md`、参考文件和脚本来执行同样流程。

代表性公开研究来源：

- [Modelling association football scores, Maher, 1982](https://www.90minut.pl/misc/maher.pdf)
- [Modelling Association Football Scores and Inefficiencies in the Football Betting Market, Dixon-Coles, 1997](https://www.research.lancs.ac.uk/portal/en/publications/modelling-association-football-scores-and-inefficiencies-in-the-football-betting-market%28d16276a2-d6e0-483b-a708-1d29663f1992%29.html)
- [Modelling football match results and the efficiency of fixed-odds betting, Goddard, 2005](https://www.stat.berkeley.edu/users/aldous/157/Papers/goddard.pdf)
- [High-frequency trading in a limit order book, Avellaneda-Stoikov, 2008](https://econpapers.repec.org/RePEc%3Ataf%3Aquantf%3Av%3A8%3Ay%3A2008%3Ai%3A3%3Ap%3A217-224)
- [Strictly Proper Scoring Rules, Prediction, and Estimation, Gneiting-Raftery, 2007](https://stat.uw.edu/research/tech-reports/strictly-proper-scoring-rules-prediction-and-estimation-revised)

## 使用对象

主要用户是想做世界杯公开分析、社交媒体内容、产品 demo、newsletter 或数据预测展示的人。

他们想看到的是简单、可传播的概率结论，例如：

```text
阿根廷胜：38%
平局：29%
法国胜：33%
判断：阿根廷略占优
置信度：中等
```

但如果有人追问“为什么可信”，skill 需要能够展开底层依据：数据来源、赔率去水、市场隐含概率、球队强度模型、校准方式、风险和不确定性。

次级使用对象是其他自动化 agent。它们可能需要把预测结果接到网页、报告、社交卡片、数据看板或后续分析流程里。因此输出需要同时支持人类可读和机器可读两种形态。

## 跨 Agent 兼容原则

skill 不应该依赖 Codex 独有能力才能理解和执行。实现时要遵守：

- 核心流程写在 `SKILL.md`，使用通用自然语言步骤。
- 公式、建模解释和输出 schema 放进 `references/`，其他 agent 可以直接读取。
- 脚本使用通用 Python，不调用 Codex 私有 API。
- 输出默认使用 Markdown，保证多数 agent、网页和文档工具都能消费。
- 可选提供 JSON 结果块，方便其他 agent 继续处理。
- 如果某个 agent 无法联网，必须要求用户提供数据源链接或原始数据，不能凭空预测。
- 所有来源链接必须保留为普通 HTTPS URL 或 Markdown 链接，不能只写来源名称。

## 对外定位

推荐对外口径：

> 基于公开数据和市场信号，估计世界杯比赛的胜 / 平 / 负概率。

默认输出不要使用赌博导向语言。可以分析赔率，因为赔率是一种市场共识信号；但不能说这是下注建议、稳赚机会、套利机会或投资建议。

推荐用词：

- 概率预测
- 市场信号
- 隐含概率
- 置信度
- 不确定性
- 风险因素

避免用词：

- 稳赚
- 必中
- 推荐下注
- 梭哈
- 投注金额
- 套利执行
- 庄家漏洞

## 为什么它是专业预测，而不是随便猜

skill 的专业性来自三件事：

1. **实时取证**  
   每次预测都要重新检索当前公开信息，而不是复用旧结论。世界杯比赛受伤停、首发、天气、赛程和市场价格变化影响很大，旧信息很快会失效。

2. **多源交叉验证**  
   不能只看一个新闻源、一个赔率网站或一个模型排名。核心输入要尽量使用多个来源互相验证，并标注信息新鲜度。

3. **概率校准而不是口号判断**  
   输出必须是概率，不是“我觉得某队会赢”。如果数据不足，要降低置信度，而不是编造确定性。

4. **证据可追溯**  
   任何重要结论都要能追到原网页、原数据或原市场页面。用户必须能点击链接回到信息源，而不是只能看到“据某网站称”。

## 信息可靠性要求

每次预测时，优先使用以下来源：

- 官方或准官方来源：FIFA、球队官网、国家队公告、赛事官方页面。
- 数据类来源：FIFA ranking、World Football Elo Ratings、公开 xG / shot data 数据源、历史战绩数据库。
- 主流体育媒体：用于伤停、首发、战术和训练信息，但需要注意时间和可信度。
- 赔率或市场来源：用于提取市场隐含概率，但必须说明赔率来源、时间和是否去水。

使用规则：

- 至少记录关键来源和检索日期。
- 重要伤停信息尽量二次确认。
- 如果只找到单一来源，必须降低置信度。
- 如果赔率来源不一致，要说明差异，不要强行合并成一个确定结论。
- 不要把社交媒体爆料当作强证据，除非它来自官方账号或被可靠媒体确认。
- 不要在首发公布前给出过高置信度。

## 来源链接和可追溯性要求

这是非常重要的产品要求：所有参考依据必须能让用户点击回到原信息位置。

输出中涉及以下信息时，必须提供可点击链接：

- 比赛时间、地点、阶段、赛制。
- 官方阵容、伤停、停赛、首发或名单。
- FIFA ranking、Elo、历史战绩、xG、射门数据等统计数据。
- 第三方分析网站的判断、模型或预测。
- 赔率页面、预测市场页面或市场价格来源。
- 天气、旅行、赛程密度等影响判断的上下文信息。

来源表建议字段：

```text
来源 | 类型 | 关键信息 | 可靠性 | 检索时间 | 链接
```

规则：

- 优先链接到最接近原始信息的位置，例如官方 match page、球队公告、数据页面，而不是二手汇总文章。
- 如果网页没有段落锚点，就链接到页面本身，并在“关键信息”里写清楚使用了哪条信息。
- 如果来源是付费墙、动态页面或需要登录，要标注“访问受限”，并尽量找公开替代来源。
- 如果一个结论来自多个来源，至少列出最关键的 2 个来源。
- 如果来源之间冲突，必须在输出里说明冲突，而不是选择性忽略。
- 不要把没有链接的“据报道”“外界认为”“市场普遍认为”当作有效依据。

## 领域权威研究如何融入

这里融入的是领域研究思想，不是人物包装。

### 1. 把赔率看作市场价格

市场效率和市场微结构研究会把价格看作信息聚合结果。映射到世界杯预测时，赔率不是“下注入口”，而是一种聚合了大量市场参与者判断的信息价格。

skill 会把赔率转换为隐含概率，并去除 bookmaker overround，得到 no-vig market probability。这个市场概率可以作为强基线，但不能被当作真相。

### 2. 把预测看作风险控制问题

市场微结构和做市模型强调：面对不确定价格和交易流，系统不能只追逐单一方向，还要控制 inventory risk。映射到预测 skill 时，就是不能只给一个激进结论，而要管理模型不确定性。

具体体现：

- 给出胜 / 平 / 负完整分布，而不是只说谁赢。
- 输出置信度。
- 标注最大不确定因素。
- 对伤停、首发、赔率波动做敏感性分析。

### 3. 引入鲁棒性思维

鲁棒建模和强化学习研究都强调在变化环境下保持稳健。映射到世界杯预测时，skill 要避免被单一异常信息带偏。

具体体现：

- 不依赖单一赔率或单一新闻。
- 遇到市场突然大幅波动时，先解释可能原因，而不是直接输出夸张结论。
- 对“信息不完整”的比赛降低置信度。
- 在技术展开中允许做情景分析，例如“如果核心前锋缺阵，概率如何变化”。

### 4. 用评估指标约束模型

专业预测不能只讲故事，而要强调算法评估。skill 后续实现时应支持回测和校准评估。

可用指标：

- Brier score：衡量概率预测是否靠谱。
- Log loss：惩罚过度自信的错误预测。
- Calibration curve：检查 60% 概率事件是否真的大约发生 60%。
- Closing-line comparison：比较模型概率与临场市场概率的差异。

## 预测范围

当前只做 FIFA World Cup。

默认预测目标：

- 90 分钟常规时间胜 / 平 / 负。

如果用户问“谁晋级”“谁夺冠”“谁赢下淘汰赛”，skill 要明确切换口径：

- 晋级概率不等于 90 分钟胜率。
- 淘汰赛晋级要考虑加时和点球。
- 输出时必须标明预测口径。

## 不做什么

skill 不做：

- 自动下注。
- 推荐投注金额。
- 资金管理。
- 串关、套利、盘口执行。
- 保证盈利。
- 帮用户选择博彩公司。
- 规避监管或账号风控。

如果用户明显要求赌球建议，skill 应该把问题重新框定为概率分析，例如：

```text
我可以帮你估计这场世界杯比赛的胜平负概率和主要不确定性，但不会提供下注金额或保证收益。
```

## 触发示例

这些请求应该触发 skill：

- “预测这场世界杯比赛的胜平负概率”
- “分析 Argentina vs France 的世界杯胜率”
- “给我巴西 vs 德国的 1X2 概率”
- “用公开数据和市场信号看这场世界杯谁更可能赢”
- “这场世界杯小组赛平局概率高吗”
- “谁更可能晋级，90 分钟和晋级概率分开讲”

## 工作流

### 1. 确认比赛和预测口径

识别：

- 两支球队。
- 比赛日期。
- 世界杯阶段：小组赛、16 强、8 强、半决赛、决赛。
- 用户要的是 90 分钟胜平负，还是晋级 / 夺冠概率。

默认使用 90 分钟胜平负。

### 2. 实时检索公开信息

除非用户明确提供完整数据并要求不要联网，否则每次预测都要检索当前公开信息。

需要收集：

- 比赛信息：日期、地点、开球时间、阶段、中立场信息。
- 球队强度：FIFA ranking、Elo 类排名、近期战绩。
- 阵容信息：伤病、停赛、预计首发、门将情况、核心球员状态。
- 足球表现：进球、失球、xG、射门质量、防守质量、定位球能力。
- 市场信号：1X2 decimal odds、赔率变化、预测市场价格。
- 背景因素：休息天数、旅行、天气、轮换、淘汰赛动机。

每条关键输入都要保留来源 URL。后续输出的“来源摘要”必须能点击回原网页。

### 3. 判断来源质量

每个关键输入要标注可靠性：

- 高：官方、权威数据源、多家主流媒体确认。
- 中：单一可靠媒体、较新的专业数据源。
- 低：社交媒体、未确认爆料、过旧信息。

低可靠性信息不能显著改变预测，只能作为风险提示。

同时建立证据表：

```text
证据项 | 当前信息 | 来源 | 可靠性 | 对预测的影响
```

这个表可以默认简化展示，也可以在用户要求“展开依据”时完整展示。

### 4. 赔率转隐含概率

如果有 decimal odds：

```text
raw implied probability = 1 / decimal odds
overround = sum(raw implied probabilities)
no-vig probability = raw probability / overround
```

输出时不要只复制赔率。必须说明：

- 赔率来自哪里。
- 检索时间。
- 是否去水。
- 市场概率只是基线，不是最终预测。

### 5. 建立组合概率

建议使用可解释 ensemble：

- 球队强度先验：Elo / FIFA / power rating。
- 足球模型：Poisson 或 xG-informed goal model。
- 市场先验：no-vig implied probability。
- 上下文修正：伤停、休息、天气、战术、赛制。
- 校准层：避免虚假精度，公开输出四舍五入为整数百分比。

如果数据不足，使用更保守的权重并降低置信度。

### 6. 默认输出格式

```text
比赛：A 队 vs B 队
预测口径：90 分钟胜平负
数据检查时间：YYYY-MM-DD

胜平负概率表
结果 | 概率
A 队胜 | 00%
平局 | 00%
B 队胜 | 00%

倾向：A 队 / 平局 / B 队 / 无明显倾向
置信度：低 / 中 / 高

主要依据
1. ...
2. ...
3. ...

关键不确定性
...

来源摘要
来源 | 关键信息 | 链接
... | ... | https://...
```

要求：

- 三个概率四舍五入后必须合计 100%。
- 不要只输出胜者，要保留平局概率。
- 不要给过度确定的语言。
- 来源摘要里的链接必须可点击。

### 7. 可选表格和可视化解释

除了默认短输出，skill 应该支持更适合公开传播或产品展示的产物形态。

可选表格：

- **胜平负概率表**：三项概率、市场概率、模型概率、差异。
- **证据权重表**：球队强度、伤停、近期状态、市场赔率、赛程背景分别如何影响预测。
- **来源表**：来源、类型、可靠性、检索时间、链接。
- **不确定性表**：关键变量、可能变化、对概率的影响方向。

可选可视化：

- **概率条形图**：A 队胜 / 平 / B 队胜三条横向条。
- **市场 vs 模型对比图**：no-vig 市场概率和最终模型概率并列。
- **证据瀑布图**：从基础强度开始，展示伤停、赛程、市场信号如何调整概率。
- **赔率变化折线图**：如果能拿到历史赔率，展示市场信息流。
- **情景分析矩阵**：例如“核心前锋出场 / 不出场”下的概率变化。

第一版 skill 可以先输出 Markdown 表格和 Mermaid / 文本式图示。后续如果要做网页或社交卡片，再扩展成 HTML、图片或 dashboard。

### 8. 机器可读输出

为了方便其他 agent 使用，用户要求“给 JSON”“结构化输出”“供程序读取”时，附加一个 JSON 块。

建议 schema：

```json
{
  "match": {
    "team_a": "A 队",
    "team_b": "B 队",
    "competition": "FIFA World Cup",
    "stage": "Group stage",
    "date": "YYYY-MM-DD",
    "target": "90_min_1x2"
  },
  "probabilities": {
    "team_a_win": 0.38,
    "draw": 0.29,
    "team_b_win": 0.33
  },
  "confidence": "medium",
  "lean": "team_a",
  "key_reasons": [],
  "uncertainties": [],
  "sources": [
    {
      "title": "source title",
      "type": "official|data|media|market",
      "url": "https://...",
      "retrieved_at": "YYYY-MM-DD",
      "reliability": "high|medium|low",
      "used_for": "injury|odds|ranking|fixture"
    }
  ]
}
```

### 9. 技术展开格式

当用户要求“展开模型”“讲硬核依据”“给回测框架”“画图解释”时，补充：

- 来源列表和提取到的输入。
- 赔率去水过程。
- 各模型组件的贡献。
- 情景敏感性分析。
- 回测指标：Brier score、log loss、calibration curve、closing-line comparison。
- 模型限制和数据缺口。
- 表格或可视化解释。

## Skill 文件规划

实现时创建：

- `SKILL.md`：触发描述、工作流、默认输出格式、安全边界。
- `references/modeling.md`：Elo、Poisson、xG、赔率隐含概率、去水、ensemble、校准、不确定性处理。
- `references/public-positioning.md`：对外传播口径、可用词、禁用词、误用处理。
- `references/output-formats.md`：Markdown 表格、来源表、可视化说明、JSON schema。
- `scripts/normalize_odds.py`：把 1X2 decimal odds 转成 raw implied probabilities 和 no-vig probabilities。

不创建：

- 任何个人研究者的资料长文。
- 静态预测结论库。
- 下注执行脚本。
- 投注金额推荐工具。

## 安全和伦理边界

- 永远不要把输出描述成金融建议、赌博建议或稳赚策略。
- 永远不要推荐投注金额、仓位、串关或下注平台。
- 明确说明预测不确定性。
- 如果用户要求“怎么下注”，只回答概率和风险，不提供执行建议。
- 对未成年人、成瘾风险或明显冲动赌博语境，要更明确地拒绝下注导向帮助。

## 验证方式

实现完成后，用至少三类 prompt 测试：

1. 小组赛：检查是否给出胜 / 平 / 负完整概率，尤其不能忽略平局。
2. 淘汰赛：检查是否能区分 90 分钟胜率和晋级概率。
3. 赌球导向请求：检查是否能拒绝下注金额和稳赚承诺，转为概率分析。

每次测试要验证：

- 是否检索当前公开信息。
- 是否给出来源摘要，并且每个关键来源都有可点击链接。
- 是否说明数据时间。
- 概率是否合计 100%。
- 是否使用赔率去水，而不是直接复制赔率。
- 是否避免“必中”“稳赚”“下注建议”等语言。
- 是否能输出 Markdown 表格。
- 是否能在用户要求时输出 JSON 结构。
- 是否能解释市场概率和模型概率的差异。

## 默认安装位置

如果用户没有指定位置，skill 默认创建在：

```text
${CODEX_HOME:-$HOME/.codex}/skills
```

这样 Codex 可以自动发现并调用。
